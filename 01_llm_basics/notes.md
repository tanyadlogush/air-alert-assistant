## Environment variables and API client

`load_dotenv()` loads variables from `.env` into the environment.

`os.getenv("OPENAI_API_KEY")` retrieves the API key from environment variables.

`OpenAI(api_key=...)` creates a client for working with the OpenAI API.

At this stage, only the API client is configured — no requests are sent to the LLM yet.


## First LLM request

`response =` the API result for this request, which contains the model-generated response and other service information.

`client.responses.create()` sends a request to the selected LLM and returns its response.

- `model` — specifies which model to use.
- `input` — contains the request sent to the model.
  * `input` can be plain text, but structured messages with different roles can be passed for conversational applications.
    In the second case, each message has a defined structure with `role` and `content` keys.
- `response.output_text` — extracts the generated text from the response.

Current flow:
Python application → OpenAI API → LLM → response → Python application


## Messages and roles

`input` can be a simple text string or a structured sequence of messages.

When using structured messages, each message has a defined structure:
- `role` — defines the role/purpose of the message
- `content` — contains the message itself

Main roles:
- `system` — general instructions (rules and behavior) and context for the model     → HOW to respond
- `user` — a specific request from the user                     → WHAT to respond to
- `assistant` — a message generated by the model
- `tool` — a result returned by a tool



## Conversation history

`messages` is a Python list used to store the conversation history  (a structured version of `input`).

Each message is a dictionary with:

* `role` — defines the role of the message
* `content` — contains the message text

Example:

```python
messages = [
    {
        "role": "system",
        "content": "General instructions for the model."
    }
]
```

During the conversation, user and assistant messages are added to the list:

```text
system → user → assistant → user → assistant → ...
```

Before each API request, the current `messages` list is passed as `input`:

```python
response = client.responses.create(
    model="gpt-4o",
    input=messages
)
```

The application manages the conversation history. The model only receives the context that is included in the current request.

### Important

* If previous `assistant` messages are not included in `messages`, the model does not see its previous answers.
* `response` is the result of the current API request; it is not the conversation history.


### Conversation flow

user_message -> add to messages  -> input=messages -> LLM -> response.output_text ->
 -> add assistant message to messages -> next user message


## `client.responses.create()`

Main parameters and capabilities:

- `model` — specifies the model used to process the request.
- `input` — contains the input sent to the model. Can be a string or a structured sequence of messages.
- `instructions` — provides instructions that guide the model's behavior.
- `max_output_tokens` — limits the maximum number of tokens in the generated response.
- `max_tool_calls` — limits the maximum number of tool calls the model can make.
- `prompt` — references a reusable prompt.
- `reasoning` — controls reasoning-related settings for supported models.
- `safety_identifier` — identifies the end user for safety monitoring.
- `store` — controls whether the response is stored by OpenAI. It is not the same as managing conversation history in `messages`.
- `stream` — enables streaming the response as it is generated.
- `text` — controls the format/settings of the generated text.
- `tool_choice` — controls how the model should use tools.
- `tools` — defines the tools available to the model.
- `temperature` — controls randomness in token selection.
- `top_p` — controls the probability mass from which tokens are selected.
- `top_logprobs` — returns the log probabilities of the most likely tokens.


## Generation parameters

`temperature` controls the randomness of token selection.
- lower values → more predictable responses
- higher values → more random/creative responses

`top_p` controls how many of the most probable tokens are considered when generating the next token.

Use either `temperature` or `top_p` to control randomness, not both at the same time.



## Structured Output: `text` → `format`

`text` — configuration of the model's output.
`format` — defines the output format.

For Structured Output:

```python
"text": {
    "format": {
        "type": "json_schema",
        "name": "air_alert",
        "schema": {...},
        "strict": True
    },
    'verbosity': 'low'    # detail of the text result
}
```

`format` can have a different structure depending on the selected `type`.

* `type` — *output format type* (`json_schema`, `json_object`, `text`, etc.).
* `name` — name/identifier of the JSON schema.
* `schema` — structure the output must follow.
* `strict` — specifies whether the model must strictly follow the schema.

Inside `schema`:

* `type` — *JSON data type* (`object`, `string`, `array`, etc.).
* `properties` — fields that can be present in the object.
* `required` — fields that must be present.
* `additionalProperties: False` — prevents additional fields not defined in `properties`.

**Important:** `properties` does not define the order of fields.



## Function Calling / Tools

`tools` — defines capabilities that the model can use by requesting the application to execute a function.

A tool has two separate parts:

- **tool definition** — describes the function to the model, including its name, purpose, and parameter schema.
- **Python function** — actual application code that performs the operation.

A **tool definition describes**:
- `name` — function name.
- `description` — what the function does.
- `parameters` — schema of the arguments the function expects.
`parameters` uses a JSON Schema structure similar to Structured Output, but describes tool input, not model output.

The model does **not** execute the Python function itself. It returns a `function_call`,
and the application executes the corresponding function.

**Basic flow:**
User → Application → Model → `function_call` → Application/Python function → tool result → Model → final answer

### Tool definition

Example:

```python
{
    'type': 'function',
    'name': 'get_air_alert_status',
    'description': 'Отримання поточного статусу повітряної тривоги у вказаному регіоні.',
    'parameters': {
        'type': 'object',
        'properties': {
            'region': {
                'type': 'string',
                'description': 'Region name'
            }
        },
        'required': ['region'],
        'additionalProperties': False
    }
}

`parameters` describes the structure of the arguments that the model should provide when calling the function.

Important fields:
`type` — identifies the output item as a function call.
`name` — name of the function the model wants the application to execute.
`arguments` — JSON string containing the function arguments.
`call_id` — identifier of this specific tool call.


## SUMMARY

`LLM` and `application` are different parts of the system.

- `LLM` generates text or structured output and may suggest using a tool. It does not execute our Python code.
- `Application`:
    - sends a request to LLM;
    - stores and passes context;
    - receives the response;
    - if the model asked for the tool, find the corresponding Python function;
    - executes it;
    - returns the result of the model;
    - decides when to end the loop and show the final response to the user.
